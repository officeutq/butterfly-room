## 反映手順と保持したもの

1. ステージング専用AWSプロファイルで接続先を確認し、SSH over SSM（AWSの管理用接続経由のSSH）で既存配置先へ接続。
2. 既存のComposeプロジェクト`current`、設定ファイル、`.env.staging`の権限600、DB名・接続ユーザーを確認。
3. 稼働中イメージに`butterfly_room_staging:rollback-before-logs-20260912`を付けて復旧用に保持。
4. サーバーのmainを早送り更新。既存の未追跡画像調査ファイル2件はそのまま保持。
5. 新イメージで接続先とエラー収集の初期化を確認後、`bundle exec rails db:migrate`を実行。追加migrationは`20260912000000`の1件で、ログテーブル2つ・索引・制約を作成。既存データ移行やseed再投入は実施しなかった。
6. 新イメージを`latest`へ付け、既存Compose設定の`up -d --no-deps --no-build --force-recreate app`でアプリを更新。`/up`成功後、同じ方法でworkerを更新。
7. 両コンテナのイメージIDと、mainの実行用ソースのSHA-256一致を確認。

サーバーの空き容量は開始時約3.3GB。通常ビルドが依存パッケージの再構築に進み容量を消費したため、完了前に中断した。
今回作成した一時展開先と未使用のビルドキャッシュだけを除去し、稼働・復旧用イメージは削除していない。

反映前後で`Gemfile`、`Gemfile.lock`、`package.json`、`package-lock.json`、`Dockerfile.production`、Ruby指定、`public`、`vendor`、`bin`、Compose設定に差分がなく、追跡ファイルの削除もないことを確認。
そのため稼働中イメージを基に、mainの`app`・`config`・`db`・`lib`・`script`を配置し、SHA-256を照合してから`npm run build:css`と`assets:precompile`を実行した。依存環境を更新するビルドではない。
最終空き容量は約3.2GB。今後、依存環境の全面ビルドを行う際は追加の空き容量を確保する。

## 機能確認

実在利用者の情報は変更せず、検証専用ユーザー4役割、非公開Store、Boothを作成した。
サーバー側の一時検証コードは`docker exec -i butterfly_room-staging-app bundle exec rails runner -`で実行し、先頭で`APP_ENV`と実接続DB名を検査した。ステージングDBに通常のテストfixtureを読み込む操作は行っていない。

### サーバー側22項目

- Store更新・Booth作成の履歴、実行者・対象・処理元・リクエストID、機密項目の秘匿化。
- 変更なし・入力不正時の非記録、必須履歴の保存失敗時の業務更新取消。
- 外側transaction（まとめて確定・取消する処理）の取消後もエラーだけが残ること。
- SQLエラーで業務用接続が利用できないtransaction内でも、別接続でエラーを保存できること。
- 同一例外の二重報告防止、404相当の例外を記録しないこと。
- 検証プロセス内だけでエラー保存を失敗させ、安全な代替出力を確認。稼働中DBの停止や権限変更は行っていない。
- 50件のページ分割、同時刻の順序、不正期間の拒否。
- 2種類のアーカイブの確認モード・適用・日数境界・再実行・本文保持・再検索。
- 実際の稼働workerで`ActiveStorage::AnalyzeJob`にnilを渡し、外部ストレージへアクセスする前の失敗を記録。ジョブID・実行回数・実行者未設定・重複なしを確認。検証した失敗ジョブ1件だけを標準のdiscard処理で除き、エラーログは保持。
- 分離したrunnerでActive Jobの再試行2回を実行し、処理済み・最終失敗の各記録を確認。再試行の受付先はこの検証内のメモリ上のアダプターに限定。
- 稼働設定を使った分離プロセスのRack（HTTPリクエスト処理基盤）経由で、認証済みのWeb例外・500応答・実行者・記録内容を確認。例外を起こす差し替えはそのプロセス内だけで、稼働中Webサーバーには適用していない。
- HTTPSの実更新と履歴の識別情報を照合し、検証アカウントの無効化まで確認。

主な経路は`Stores::UpdateService` / `Booths::UpdateService` → `Logs::ChangeTracker` → `Logs::RecordChangeService`、Rails / Active Job → `Logs::ErrorSubscriber` → `Logs::RecordErrorService`。

### 実ブラウザー・HTTPS側47項目

Chromiumで実際にログインし、稼働中Webサーバーに対して確認した。

- 未認証はログインへ誘導。customer（視聴者）・cast（配信者）・store_admin（店舗管理者）は両ログの一覧・詳細すべて403。system_admin（システム管理者）はすべて200。
- 権限外の店舗更新を拒否。ダッシュボードからログ画面へ移動可能。
- HTTPS経由でStore・Boothを更新し、共通change_logsから検索・詳細表示。変更なしでは履歴を追加しない。
- HTMLを含む検証用文字列が実行されず文字列として表示され、説明文の実値が表示されない。
- ページ送りの50件→2件、条件保持、不正期間、2種類のアーカイブ済みログの再参照。
- 今回mainに含まれるプロフィール詳細・編集、ブース情報・編集の画面が200。
- 一覧・詳細4画面を1440px／390pxで撮影し、表示と画面全体の横はみ出しがないことを確認。
- 2接続並行で計10回の一覧検索に成功。HTTPS往復時間は中央値84ms、最大147ms。

画面の経路は`SystemAdmin::BaseController` → ログ用Controller → `Logs::SearchQuery` → 一覧・詳細テンプレート。

## ステージングでの検索性能

各テーブルに合成データ1万件、180日間へ分散、半数アーカイブ済みを用意し、実際のQuery（検索処理）と`EXPLAIN (ANALYZE, BUFFERS)`を実行した。
検証は種類ごとのtransaction内で行い、最後に全合成データを取消。SQLの実行上限3秒・ロック待ち上限200msを設定した。

| 条件 | 更新ログ Query / DB実行時間 | エラーログ Query / DB実行時間 |
| --- | --- | --- |
| 直近7日 | 73.00 / 0.054 ms | 63.00 / 0.125 ms |
| 180日＋実行者 | 13.28 / 0.222 ms | 10.98 / 0.500 ms |
| 180日＋店舗 | 25.85 / 0.667 ms | 10.30 / 0.360 ms |
| 180日＋アーカイブ済み | 11.57 / 0.099 ms | 10.68 / 0.177 ms |
| 180日・100ページ目 | 11.83 / 4.133 ms | 15.29 / 6.006 ms |
| 対象 / 重要度 | 9.43 / 0.063 ms | 12.31 / 0.117 ms |

通常の期間・実行者・店舗・対象・重要度検索で対応する索引を利用した。
この件数・分布で100ページ目へ進む検索は、DBが全走査と並べ替えを選び、4〜6ms程度で完了した。索引使用を強制する変更はしていない。
アーカイブ済みの検索は日時索引を利用。Query時間には初回のモデル読込等も含み、DB時間は後続の別実行である。

既存の実分布でも一覧・詳細・検索を確認したが、当時のログは検証用の少量データが中心。
本番の大量データ、ピーク負荷、長期間の容量増加、DB停止を伴う試験は実施していない。今回の測定を本番での性能保証とは扱わない。
