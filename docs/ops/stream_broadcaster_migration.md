# 旧配信の配信開始者を移行する手順

対象：#1280 / #1287 / #1288 / #1289。今回の実装作業ではステージング・本番への適用も、実データの補完も行わない。以下は後日、対象環境と差分を確認して実行する手順である。

## 1. 新旧配信方式の切替

先にIAM（AWSのアクセス権限）の差分を確認する。実行するアプリには `ivs:CreateParticipantToken`、`ivs:GetStage`、`ivs:ListParticipants`、`ivs:GetParticipant`、`ivs:DisconnectParticipant`、履歴調査には `ivs:ListStageSessions` が必要。ステージングのTerraform定義には既存のStage ARN・環境タグ制限を保ったまま不足する読み取り操作を追加しているが、今回applyはしない。本番は既存の管理ポリシーを対象環境で確認し、対象Stageに限定した権限差分を別途適用する。棚卸し時の本番ポリシーには一覧・切断操作も不足していたため、コード更新だけで成功すると判断しない。

1. 旧方式の準備・トークン発行・配信開始の入口を停止する。稼働中のセッションを一覧化し、利用者に終了を案内する。途中の旧セッションを作成者の配信実績へ自動確定しない。
2. DBのバックアップを取り、切替基準日時（UTC）を固定する。旧アプリがトークンを発行できないことを確認してからスキーマ変更・新コードを適用する。同時に旧ブラウザーへ画面の再読み込みを案内する。
3. スキーマ変更は既存ブースの `publisher_blocked_until` を変更時点の12時間1分後に設定する。旧トークンの発行時刻や参加者IDを全件記録していなかったため、期限前の再発行は停止する。新規ブースにはこの初期制限を設けない。
4. 現在参照を持つ旧セッションは管理終了・閉鎖の正規手順で処理する。IVS照会や切断が失敗したら、現在参照をSQLで消して進めない。旧セッションを管理終了したブースには、その時点から12時間1分の制限を再設定する。管理終了でも記録済みの金額・配信者を消さない。
5. 制限の期限後も、接続中の配信者がいるブースは新規発行を拒否する。開始記録不明のまま稼働している旧配信は、再接続も含めて新方式へ自動昇格させない。管理終了後、新しい準備を作成する。
6. 小さな検証用ブースで下記の実IVS確認を行い、問題がなければ運用を再開する。旧プロセスや旧APIへ経路が残っていないことを確認する。

この待機は既存ブースでの配信再開に影響する。メンテナンス日程を決める前に確認する。トークンの期限切れだけで接続が終了したとは判断しない。また、切断APIを未知の旧トークン全件の失効手段として扱わない。

## 2. 作成者からの補完（#1289）

RailsのRakeタスクはServiceを呼び出すだけで、対象の判断と更新はServiceが行う。

```sh
# 日時・出力先は実際の移行基準へ置き換える。出力ファイルは新規作成のみ。
CUTOFF=2026-09-13T00:00:00Z OUTPUT=/secure/stream-broadcaster-plan.json bundle exec rails stream_broadcasters:preview

# 上記の対象IDと前後値をレビューしてから、同じファイルで適用する。
PLAN=/secure/stream-broadcaster-plan.json bundle exec rails stream_broadcasters:apply
```

事前確認で出す計画は、基準日時・レコードのスナップショット・対象/除外理由・変更前後の利用者ID・関連台帳額・配信時間・消化コメントIDを含む。氏名、メール、参加用トークンは含めない。ファイルはアクセス制限された作業場所に保管し、リポジトリへ追加しない。

対象条件はすべて必要：

- 旧方式で、作成時刻・準備開始時刻が基準日時以前。
- `status = ended` かつ `ended_at` が基準日時以前。
- `broadcast_started_at` があり、準備開始 ≤ 配信開始 ≤ 終了。
- 配信開始者と由来が空欄。
- 現在のブースから参照されておらず、店舗の紐づけが一致。

開始時刻がないものは全件除外する。配信していなかったとは断定しない。準備中・配信中・離席中、移行後に作成/終了したもの、新方式、確定/補正済み、不整合も除外する。

適用は固定した計画内の対象だけを1件ずつ処理し、実行時に条件とスナップショットを再確認する。中断後は同じ計画で再実行でき、設定済みの実績を上書きしない。途中で新しい計画を作って対象を広げない。元の作成者・各時刻・状態・店舗/ブース・台帳・返却・精算・コメントは変更しない。

適用結果と実行ログを保存する。適用前後に店舗・ブースの台帳合計、消化・未消化・返却件数、精算データが同じことを確認する。個人別には「不明→作成者」へ帰属が移る。移動する配信時間は対象月と重なる範囲に限られる。補完で推測の開始時刻は作らない。

取り消しが必要な場合は、同じ計画だけに対応する次のタスクを使う。後から証拠補正した実績は取り消さない。

```sh
PLAN=/secure/stream-broadcaster-plan.json bundle exec rails stream_broadcasters:rollback
```

## 3. 証拠調査と限定的な補正（#1287）

```sh
SESSION_ID=123 bundle exec rails stream_broadcasters:investigate
```

指定配信と時間が重なるIVSセッションをページ分割し、保存された配信者属性を照合する。結果は `identified`（一意）、`unknown`（証拠不足）、`ambiguous`（複数）。IVSエラーは調査失敗であり、証拠がないという結果へ変換しない。記録の保存期間外・アプリログ未保存の場合、過去の本人を復元できるとは限らない。実環境ごとの保持状況を調査記録へ残す。

補正する場合は調査結果や利用可能なログを確認して、次のような具体的計画を作る。作成者・担当者・既存補完値だけを本人の証拠にしない。証拠の参照先と判断理由を必須とする。

```json
{
  "stream_session_id": 123,
  "from_user_id": 10,
  "from_source": "legacy_creator_backfill",
  "to_user_id": 20,
  "evidence_reference": "保管したIVS調査記録の識別子",
  "reason": "配信済み参加者のセッション・役割・利用者属性が一意に一致",
  "comments": [{"id": 456, "from_user_id": 10}]
}
```

空欄から追記する場合は `from_user_id` と `from_source` を `null` にする。`comments` は確認した消化自動コメントだけを列挙し、補正しない場合は空配列とする。

```sh
PLAN=/secure/broadcaster-evidence.json bundle exec rails stream_broadcasters:evidence_preview
PLAN=/secure/broadcaster-evidence.json bundle exec rails stream_broadcasters:evidence_apply
```

事前確認には利用者の前後、移る台帳額・時間、店舗総額の差分0、指定コメントの前後を出す。対象は終了済み旧配信だけで、配信時の本人記録は補正対象外。計画後に変更された記録は拒否する。適用時は旧補完の根拠を保持したまま補正履歴を追記する。通常チャット、操作監査、台帳、精算は変更しない。誤った証拠補正の修正も、変更前の値・由来を明示した別計画で行う。

## 4. 実環境の確認項目と切り戻し

- X準備→Yトークン→Y映像/音声→Y確定。Xの別タブ、別端末、直接URLからの割込み拒否。
- 同じ本人が二つのブースで同時に開始。一つだけ開始権を得る。
- 参加失敗、開始確認前の画面離脱、確定応答消失、期限切れ前後の再接続。本人と初回時刻を維持する。
- 再接続後の古い終了/状態要求の拒否、通常終了と管理終了、切断API失敗時に終了や返却を先行させないこと。
- 終了後に旧トークンを再利用しようとした場合、次の開始を妨害/重複しないこと。1分トークンでの継続配信・SDKの再接続挙動、IVS反映遅延に対する確認の再試行。
- 新旧ブラウザー混在、閉鎖と開始の競合、準備のみ閉鎖、非公開店舗・ゲスト・退会済み利用者の表示。
- 補完対象、除外理由、未補正件数、個人別帰属差分、店舗/ブース総額と返却・精算不変。

切り戻す場合はまず配信開始口を停止し、稼働中と残存トークンを確認する。DBの人物列・開始権・根拠は保存し、データのバックアップなしにスキーマを戻さない。旧アプリはこの開始権を理解しないため、配信を開けたまま旧版へ戻さない。原因修正後に新方式へ戻すか、再度旧トークンの最終発行から有効期間を待つ切替計画を作る。補完データの取り消しとアプリの切り戻しは別に判断する。

実装時点の実環境のデータ件数・適用件数・未補正件数は未調査。ローカルの代替応答による確認を、実IVS・ステージング・本番の適用実績として記録しない。
