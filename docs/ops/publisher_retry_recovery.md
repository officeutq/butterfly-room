# 配信接続の有限再試行と運用復旧（#1336 / #1340）

2026-09-17。#1337〜#1339の後に適用する。同日、利用者の指示により[ステージングへ反映](publisher_retry_staging_verification.md)した。本番は未反映。実機・実AWSの確認は下記の検証記録で未実施と区別する。

## 通常の結果

- 開始確認と切断は、初回に加えて0.5秒・1秒・2秒で最大3回。API応答時間・ジョブの待ち時間を含めて3.5秒以内という保証ではない。
- 通常終了は手元の送信を止め、DB終了・未消化返却が確定すればリザルトへ進む。強制終了通知の受信側も同じセッションを照合して止める。
- 切断が全失敗なら自動再試行を止め、未確認の開始権を保持する。同じ人物・ブースの次回配信は保留。画面やログインのやり直しでは解除しない。
- DBの終了・返却が完了したことと、AWS切断が確認できたことは別。終了通知とAWS切断が両方失敗する場合の即時停止を保証しない。新しい配信継続監視は追加していない。

## 展開時の確認

1. 対象コード・環境・DBとバックアップを確認する。今回のmigrationは`20260917000000`・`20260917010000`・`20260917020000`。旧配信履歴や人物の補完を再実行しない。
2. appとworkerを同じ版へ揃える。旧workerは無期限の切断処理を実行し得るため混在させない。旧ブラウザーの再確認POSTは廃止済みであり、更新を案内する。
3. 既存未解決レコードを記録する。導入前に4回以上試行済みの行は、回収時に5回目を呼ばず最終失敗へ移す。古い予定ジョブも新コードの回数と予定を守る。
4. productionの`RetryPendingPublisherDisconnectsJob`の毎分回収、Solid Queueのworker・schedulerが稼働していることを確認する。ローカルdevelopmentの既定Asyncアダプターはプロセス再起動で予定を失うため、検証時にジョブを失った場合は対象IDのジョブか回収ジョブを明示実行する。新規環境変数・IAM権限は不要。
5. 通信前に試行回数・処理中日時・30秒後の期限をDB確定する。通信後のDB保存障害・プロセス停止では、期限後にその1回を応答未確認として消費し次の有限再試行へ進む。DB障害で回収自体が止まっている間は確認済みへ補完しない。
6. 同じDB内はアカウント・リージョン別に0.25秒間隔。別DBや運用ツールとの合計がAWS枠を超える場合も有限回の失敗として扱う。`retry_limit=0, max_attempts=1`を維持する。

## 最終失敗の復旧

システム管理者のエラーログで`RetryExhausted`と関連する人物・店舗・配信セッション・要求UUIDを特定する。接続行の`last_disconnect_error`、通常ログの接続ID・処理元、AWS側の権限・通信・呼出制限を照合する。トークン文字列は不要。

対象環境で、まず表示だけ実行する。以下のIDは例であり、ログで特定した対象に置き換える。

```bash
bundle exec rails runner script/recover_publisher_disconnect.rb --connection-id 123
```

出力の環境・DB・要求UUID・Stage・参加者IDと、終了・返却済みか／再接続取消なのかを確認する。原因を修正した後、確認した値を全て明示して1回だけ切断する。

```bash
bundle exec rails runner script/recover_publisher_disconnect.rb --connection-id 123 --apply --environment production --database EXPECTED_DB --request-id EXPECTED_UUID --participant-id EXPECTED_PARTICIPANT --stage-arn EXPECTED_STAGE_ARN
```

- 指定値が一致しない場合は実行しない。最終失敗でない通常配信中の接続へ運用切断を広げない。
- API成功後だけ`disconnected_at`・`released_at`を記録する。試行回数は加算し、過去の最終失敗日時は保持する。終了・返却・人物・売上を変更しない。
- 運用の1回も失敗した場合は終了コード1、未確認のまま保持する。新しい自動3回を始めず、原因確認に戻る。通信中のプロセス停止では30秒の期限を過ぎてから同じ指定で状態を処理し、未確認のままなら改めて対象を確認する。
- 保存済み参加者IDへのAPI成功を確認できない限り、参加者の不在・期限切れ・404だけで`released_at`を手入力しない。Stage削除、履歴削除、全件一括切断を復旧手順にしない。
- 復旧後は表示コマンドで`disconnected`を確認し、リザルト・管理画面と同じ人物／ブースの次回開始可否を確認する。別の配信中・非公開・閉鎖・権限不足の制限は解除されない。

## 戻す場合

保存済み回数・失敗・履歴を維持し、migrationを取り消して列を削除しない。旧コードへ戻すと旧workerが上限後も切断を再試行し、旧ブラウザーは新コードで廃止したAPIを呼ぶため、app／workerを止めずに片側だけを戻さない。切断上限を保つ修正版への切替を優先する。
