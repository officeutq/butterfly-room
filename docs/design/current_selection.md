# ブース・店舗選択の共通契約（#1255 / #1271）

2026-09-15に整理した共通契約。変更前の調査基準は`835e024b782089a65fd65b42f79f7de4b0b9ddfa`。共通判定・保存境界・#1274のサーバー入口・#1275の画面統合・#1276の準備切替案内は2026-09-16にmainへマージ済み。10節のD01・D02はユーザー合意済み。店舗変更とキャスト招待承認成功時の例外を含め、以下を採用仕様とする。

2026-09-16の接続内容は[41項目の入口対応表](current_selection_entries.md)を参照する。PCでのキャスト・システム管理者による利用者確認は[ローカル確認記録](../ops/current_selection_local_verification.md)、環境反映・追加確認・実機確認の残項目は[ステージング記録](../ops/current_selection_staging_verification.md)に記載する。操作手順は[共通操作](../user_manual/current_selection_manual.md)。本番へは未反映。以下の担当Issueの記述は設計時の境界も含み、適用範囲は対応表で管理する。

実配信者の記録・配信制御は#1280で実装・有効化済み。[実配信者設計](actual_publisher.md)の共通情報を使う。Xは準備作成者、Yは実配信者、Zはブース担当者。選択の保存先は引き続きログインsession（ブラウザーの認証セッション）の`current_booth_id`・`current_store_id`とし、選択を配信セッションや配信者の記録へ転用しない。

## 1. 対象と候補

| 役割 | ブース候補 | 手動選択できる店舗候補 |
| --- | --- | --- |
| キャスト | 未閉鎖で本人の`BoothCast`があるブース | 店舗の単独切替は提供せず、選んだブースの所属店舗を保持 |
| 店舗管理者 | admin所属のある全管理店舗のブース。閉鎖済みも含む | admin所属のある全管理店舗 |
| システム管理者 | 全店舗のブース。閉鎖済みも含む | 全店舗 |
| 視聴者・未ログイン | 管理用の選択なし | 管理用の選択なし |

- ブース候補を選択中店舗の中だけに限定しない。他者の配信中・離席中も候補に含める。
- 閉鎖済みの表示フィルターと候補総数を分ける。現役1件＋閉鎖済み1件は、管理者にとって候補2件。
- 非公開店舗を公開閲覧不可という理由で管理候補から除かない。存在・所属・役割を毎回検証する。
- 選択可能と、編集・共有・準備・配信開始が可能かは別の条件。閉鎖済みへの選択許可を、各操作の許可に流用しない。

## 2. ブース・店舗の判定表

### 2.1 ブース

| 条件 | 決定する選択 | 手動変更・モーダル |
| --- | --- | --- |
| 候補0件 | 未選択。必要操作では候補なしを案内 | なし |
| ① 候補1件 | 唯一の候補へ自動設定して固定 | なし |
| ② 候補複数・本人の整合する配信中／離席中が1件 | 本人Yのブースと所属店舗へ自動設定して固定 | なし |
| ③ 候補複数・本人未配信・有効選択あり | 現在の選択を維持 | ヘッダーで操作した時だけ表示 |
| ③ 候補複数・本人未配信・未選択または無効 | 無効IDを除去し、未選択を維持 | 必要操作へ進む時、またはヘッダー操作時に表示 |

①には店舗変更時の例外がある。唯一のブースが別店舗にある場合は、選択した店舗とブース未設定を維持し、ブースが必要な操作時にだけ唯一のブースと所属店舗を自動設定する（5節・D01）。本人配信の固定先が候補外などの不整合は、単純な候補数で別対象へ上書きせず3節に従う。

### 2.2 店舗（店舗管理者・システム管理者）

| 条件 | 決定する選択 | 手動変更・モーダル |
| --- | --- | --- |
| 候補0件 | 未選択。店舗が必要な操作は候補なしを案内 | なし |
| ① 候補1件 | 唯一の店舗へ自動設定して固定 | なし |
| ② 候補複数・本人の整合する配信中／離席中が1件 | 本人の配信ブースの所属店舗へ固定 | なし |
| ③ 候補複数・本人未配信・有効選択あり | 有効な選択を維持 | ヘッダーまたは店舗選択カードから共通モーダル |
| ③ 候補複数・本人未配信・未選択または無効 | 無効IDを除去し、未選択を維持 | 店舗が必要な操作、または明示的な店舗選択操作で表示 |

店舗選択カードの最終構成は#1253。**選択済みブースの通常の手動変更はヘッダーからのみ。** 明示的な店舗変更後の再設定（D01）とキャスト招待承認成功後の自動切替（D02）は例外とする。店舗は従来合意した条件付きの選択カードも使う。本人配信中や店舗1件では、そのカードも切替入口として表示しない。

### 2.3 共通の原則

- ①②は未選択・別対象選択でも有効な固定先へ補正する。ただし①はD01の店舗変更後の未設定を尊重する。配信中の切替確認は廃止し、切り替えるには先に本人が配信を終了する。
- ③の有効な選択を、URL・通常の保存・再読込・招待の表示・準備作成者を根拠に変更しない。例外は明示的な店舗変更（D01）とキャスト招待の承認成功（D02）に限定する。
- 配信終了後は、同じブースの選択を維持する。終了によって候補複数・本人未配信になれば手動変更できる。
- 準備画面で開始成功が確定した時点で、再読み込みを待たずヘッダーのブース・店舗を名前だけの表示にする。開始応答消失後の状態確認で本人配信を確認できた場合も同じ扱いとする。別タブでの開始などにより古いヘッダーから選択モーダルを要求した場合は、画面を再移動せず終了が必要な旨を案内し、ヘッダーを固定先の名前に更新して切替リンクを外す。選択候補は表示せず、配信接続と入力を保持する。未選択の必要操作から固定先へ進む既存の自動案内とは区別する。
- 管理者が選択中のブースを閉鎖しても、その選択を維持する。キャストは閉鎖済みを候補から除き、通常の0／1／複数ルールで再判定する。
- 不正な切替先・権限のないURLを拒否しても、元の有効な選択は消さない。元の選択自体が無効な場合だけ除去する。
- 選択の自動設定・モーダルの表示・情報取得だけで配信準備、Stage作成、配信開始・終了を行わない。
- 視聴者数の定期取得と視聴の生存通知では、選択の自動設定・ログインsessionのCookie再発行を行わない。切替前に開始した通信が後から完了しても、新しい選択を古いCookieで巻き戻さない。認証・公開範囲・BAN判定とPresenceのDB更新は維持する。

## 3. 本人判定・不整合・競合

選択・招待の本人判定は`StreamSession.current_broadcast_for_selection(user)`を使う（#1272）。既存の`actually_broadcasting_by(user)`と同じ現在配信の条件に加え、`publisher_recording_state`で記録の整合性を確認する。新しい本人判定のためにXやZへ代替せず、正常な参照ではIVSへ通信しない。

| 状態 | 選択側の扱い |
| --- | --- |
| 本人の整合する現在配信が1件 | 同じY・ブース・店舗を固定の根拠にする |
| 旧準備だけ／トークン発行だけ／初回成功確定前 | 本人配信中と数えない。候補数に従い選択可能 |
| 本人配信の再接続中 | Yと初回時刻・現在配信が維持されている間は固定を維持 |
| 終了済み履歴／終了後の切断待ちだけ | 現在の本人配信と数えない。次の配信の切断確認は既存Serviceが担当 |
| 他者の整合する配信のみ | 本人未配信として選択できる。その対象の準備・開始は既存Serviceで拒否 |
| 本人に紐づく未終了記録の欠落・矛盾、本人の現在配信が複数 | 未配信と判断しない。固定先を推測せず、変更を保留して再確認を案内 |
| 本人の固定先が権限外・閉鎖済み・所属店舗と矛盾 | 権限を拡張せず、無効対象を操作させない。自動終了・他者への代替も行わず、再確認を案内 |
| 別人・人物不明のブースに不整合がある | Xやアクセスした利用者を配信者にしない。そのブースの配信可否は共通配信制御へ任せ、他の正常なブースの情報閲覧まで止めない |
| DB参照に失敗 | 選択を新たに確定しない。再試行可能なエラーとして扱う |

`actually_broadcasting_by`が0件という理由だけで、本人ID付きの矛盾した未終了記録を見落とさない。#1272の参照は、保存済みYが本人で、配信セッションのstatusがlive、終了時刻が未設定、またはlive／awayブースが現在セッションとして参照する記録を検査する。最大2件を読み、複数なら固定先を推測しない。終了済みで現在配信の参照もない履歴は検査対象外とする。

| `current_broadcast_for_selection`の結果 | 呼び出し側の扱い |
| --- | --- |
| 整合する`StreamSession`が1件 | `booth`・`store_id`を本人固定の根拠にする。候補・権限の検証は#1273で行う |
| `nil` | 本人の現在配信・矛盾する未終了記録なし。候補数と有効選択の維持へ進む。開始権だけでは固定しない |
| `StreamSession::CurrentBroadcastInconsistent` | 未配信へ読み替えず、変更・招待承認を保留して再確認を案内する |
| DB参照の例外 | そのまま呼び出し側へ伝える。空き・未配信として選択を確定しない |

ブース状態・現在参照・人物記録に加え、閉鎖済みの本人配信と配信セッション／ブースの店舗不一致も不整合とする。人物不明を準備作成者Xや接続の所有者から推測しない。読み取りは都度DBへ問い合わせ、sessionや配信状態を保存せず、IVS通信・修復を行わない。

この参照の利用は#1273の共通選択、#1279の招待承認確認から接続する。#1274でログイン・現在対象・全入口へ適用し、#1276は準備画面に接続する。#1272だけで既存入口の自動選択を置換したり、開始・終了Serviceの既存判定を変更したりしない。`test/models/stream_session_selection_test.rb`でC02・C11と準備・開始権・再接続・終了・履歴・他者の区別を確認する。

別タブ・別端末は次のアクセス・操作時に最新DBを参照する。全端末の画面を即時に強制移動する仕組みや、session変更後に配信を終了する処理は追加しない。モーダル表示時は未配信でも、確定時に本人配信が成立していれば別対象への変更を拒否する。

開始成功確定・選択確定・招待承認が競合する場合、確定順を基準に最新の状態を判定する。本人配信の一意制約だけでは招待承認との競合を防げないため、#1279では`ConfirmPublisherService`と`AcceptInvitation`が本人のUser行を`FOR NO KEY UPDATE`で先にロックする。開始確定はUser→ブース→配信セッション→接続、承認はUser→招待→新規所属・ブースの順に処理し、外側のトランザクション確定まで本人のロックを維持する。退会のUser先行と揃え、新規接続の外部キー参照とは競合させない。

開始成功が先に確定した場合、待機した承認は最新の本人配信を確認して拒否し、招待消費・所属・ブース・Stage作成を行わない。承認が先なら承認を完了し、その後の開始成功まで一律に禁止しない。未確定の開始権は本人配信と数えず、招待承認から取消・配信終了を起こさない。開始成立後の選択補正は#1274で共通処理に接続する。通常の選択は各操作時の共通判定、招待と開始のDB確定はこの直列化で区別する。

## 4. 選択処理の責務と呼び出す契機

| 処理 | 入力と責務 | 保存・配信への影響 |
| --- | --- | --- |
| 共通判定 | 認証利用者、保存済みブース・店舗ID、必要対象、操作目的。候補・本人配信・選択の有効性・変更可否・理由を返す | 判定だけではsessionも配信状態も変更しない |
| 自動設定・無効選択の整理 | ログイン完了、選択を利用する画面の通常アクセス、必要操作で共通判定を利用 | 許可された固定先／未選択だけを保存。D01の店舗変更例外を尊重 |
| ブース選択の確定 | 共通モーダルでの選択POST。対象を再認可し、最新条件を再判定 | 成功時にブースと所属店舗を一組で保存 |
| 店舗選択の確定 | 店舗選択POST。変更と同一店舗確認を分ける | 実際の店舗変更だけブースを解除。後続の決定は5節 |
| キャスト招待承認後の選択 | 承認Serviceが成功した結果のブースを使う | 成功時だけブースと所属店舗を一組で保存し、切替を通知。表示・失敗では変更しない |
| 表示用参照 | 同じリクエストで確定した共通結果をヘッダー・本文へ渡す | ヘルパー独自の最小ID補完、paramsによる対象代替をしない |
| 対象を持つ業務処理 | URL・フォームの対象と共通選択を認可後に照合 | 対象不一致を別対象へ読み替えず6節の応答 |

共通の判定・業務処理はService（業務処理を集約するクラス）、sessionの読み書きとHTTP応答はController（リクエストを受ける層）の共通接続箇所へ集約する。既存の公開APIをそのまま使える箇所に、本人判定だけの中継クラスを増やさない。選択のためのDBテーブルや別の配信状態は追加しない。

### 4.1 共通処理の呼び出し（#1273）

`CurrentSelectionService.new(actor:, current_booth_id:, current_store_id:, purpose:, target_id:).call`で判定する。役割・所属・本人配信は呼び出すたびにDBから確認する。候補一覧は全権限範囲のまま返し、画面で閉鎖済みを非表示にしても判定の候補数を変えない。

| `purpose` | 用途 |
| --- | --- |
| `normalize` | ログイン・通常アクセスで無効選択を整理し、本人配信・唯一候補を設定する。D01の別店舗管理中の未設定を維持 |
| `require_booth` | ブースが必要な操作。D01の未設定から唯一の候補を所属店舗と組で設定。複数なら未設定を返し、呼び出し側でモーダルへ |
| `require_store` | 店舗が必要な操作。店舗未設定・複数なら呼び出し側でモーダルへ。別店舗のブースは補完しない |
| `select_booth` | 選択POSTの対象IDを候補と本人固定条件で再検証し、ブースと所属店舗を設定 |
| `select_store` | 店舗選択POST。同一店舗はブースを保持し、変更なら5節D01に従って解除・再設定 |
| `invitation_accepted` | 承認Service成功後のキャスト専用。結果のブースIDを渡してD02を適用。本人配信があれば拒否 |

結果は`booth`・`store`・全候補`booths`・`stores`・本人`broadcast`・`error`を持つ。`success?`、`booth_switchable?`・`store_switchable?`、`booth_fixed?`・`store_fixed?`で各入口を揃える。`not_selectable`は不正／権限外の対象、`broadcast_fixed`は本人配信による変更拒否、`broadcast_inconsistent`は本人の不整合または固定先の権限喪失。DB例外は未配信へ変換せず呼び出し側へ伝える。

`CurrentSelection`（Controllerの共通モジュール）の`resolve_current_selection`で保存済みIDを渡し、`save_current_selection`で成功した結果だけをsessionの2キーへ保存する。未設定は当該キーを削除し、他のログイン情報を保持する。拒否・判定失敗では保存しない。保存した結果を`@current_selection`へ保持し、ヘッダーと本文へ同じ結果を渡す。配信準備が必要な入口は既存Serviceの成功後に保存する。

`purpose`は呼び出し側で固定し、HTTP入力の操作名をそのまま受け付けない。特に`invitation_accepted`は承認成功後にだけ呼び、招待の表示・失敗・再表示からは呼ばない。共通処理自体は配信準備・Stage作成・通知・画面遷移を行わない。

#1273は共通判定と保存箇所を用意し、#1274で既存の選択入口・参照を接続した。ヘッダー・キャスト旧一覧撤去・準備切替は#1275・#1276でローカル実装済み。管理者の旧一覧・カードと閉鎖済み情報の操作表示は#1291〜#1294の後続範囲。`test/services/current_selection_service_test.rb`と`test/controllers/concerns/current_selection_test.rb`で判定と保存を確認する。

- ログイン、通常アクセスの固定補正と、ユーザーが候補を選ぶPOSTを分ける。先読み・候補表示GETを手動選択として扱わない。
- `return_to_key`等の許可した画面種別から、確定した対象のpath helperで戻り先を組み立てる。古いAの`return_to`をそのまま使ってB選択後にAへ戻さない。
- キャンセルでは選択・入力・画面を保持。未保存確認は選択POSTの前に行い、通信失敗でも旧画面を勝手に別対象へ描き替えない。
- sessionの値は端末ごとに異なり得る。共通判定を通していないCookieや画面表示だけを、現在の配信や更新権限の根拠にしない。

## 5. 店舗変更後のブース再設定

現行の`Admin::CurrentStoresController#create`と`Admin::StoresController#select_modal`は、店舗IDを設定してブースIDを解除するだけで、変更先店舗のブース検索を呼ばない。後続の`Cast::BaseController#current_booth`が全管理店舗の最小IDを表示用に補完し、編集・履歴のGETがURLの対象を保存する。これが、B店を選んだ後に表示や選択がAへ戻る原因になる。

「店舗変更時の現行処理を引き継ぐ」は、この店舗設定・ブース解除の契機を共通処理へ接続する意味とする。表示だけの最小ID補完、他者配信優先、旧URLによる巻き戻りを残す指定とはしない。

1. 同一店舗の確認では、有効なブースを解除しない。
2. 本人配信中は別店舗への変更を拒否し、本人のブースと店舗を維持する。
3. 本人未配信で店舗Bへの変更を確定したら、店舗Bを保存して従来のブース選択を解除する。
4. 全店舗の有効なブース候補が1件で変更先店舗に属する場合は、そのブースを自動設定する。唯一の候補が別店舗に属する場合、または候補0件・複数の場合は、変更先店舗を維持してブース未設定にする。変更先店舗内だけへ候補を絞ったり、複数から最小IDを既定値にしたりしない。
5. 変更先店舗でブース未設定の場合、通常の店舗情報・ダッシュボード表示や再読込だけで別店舗のブースを補完しない。ブースが必要な操作へ進んだ時に、全店舗の候補0／1／複数による未選択時のルートを使う。唯一の候補ならモーダルなしでそのブースと所属店舗へ、複数なら共通モーダルへ、0件なら候補なしの案内へ進む。
6. ブースを必要とする操作の対象を確定した時は、ブースと所属店舗を一緒に保存する。店舗とブースの見かけ上だけの不一致を作らない。本人配信が成立していれば2項の固定を優先する。

### 6.1 選択変更後の画面

| 元の画面 | ヘッダーでBへ変更した後 | 担当 |
| --- | --- | --- |
| 管理用ブース情報 | B情報 | #1275、ダッシュボードの受入確認#1254 |
| ブース編集 | 編集可能ならB編集。閉鎖済みならB情報 | #1275、閉鎖済みの操作表示#1292 |
| ブースの配信履歴一覧 | B履歴 | #1275 |

| 管理用店舗情報・各編集 | 店舗Bの同種画面へ。通常の保存・戻るはB店舗情報へ | 新規画面#1251・#1252 |
| 既存の選択店舗に連動する管理画面 | Bの対象へ。入力があれば事前に破棄確認 | #1274・#1275 |

配信準備から他者配信中Bへ移る場合は、選択を許可し準備を作らないという採用要件から、B情報で案内する案を設計上の実装先とする。Bの選択でAの準備画面を操作可能なまま残さない。準備に失敗した場合は、元の有効な選択・画面を維持し、Bを空きと扱わない。

`Booths::PrepareSelectedBoothService`が既存の準備Serviceへ委譲し、閉鎖済み・共通制御で他者配信と確定した対象を情報確認へ分岐する。選択のPOSTは準備に成功してから保存し、保存直前にも共通選択を再確認する。DB不整合や通信失敗は選択成功としない。店舗変更後にブースが未設定となる場合はダッシュボードへ戻し、以降の必要操作で共通選択へ進む。

準備画面を離れる前に加工プレビューを破棄し、進行中の初回開始要求は既存の取消手順で回収する。旧準備や保存済みタイトルは、切替だけを理由に終了・削除しない。`selection_switch_controller.js`は実際の`window.publisher`に開始要求の回収を依頼し、未確定の取消結果を確認できなければ選択POSTを送らない。既に成功確定した配信は自動終了せず、別端末での終了も含めサーバーの最新DB判定に従う。切替失敗時は元の画面を保持し、取消後の未配信準備ならプレビューを復帰できる。SDKの映像送信中は本人固定が働く。配信タブを離れれば媒体の送信が止まる現行の破棄処理と、DBの配信継続は同義ではない。

### 6.2 直接URLと不一致の案内

#1275ではヘッダーと店舗選択カードを共通結果の切替可否に接続した。旧キャスト一覧GETは認可後ダッシュボードへ戻し、一覧テンプレート・カードを撤去した。管理者の閉鎖済みも同じ選択モーダルで明示する。`selection_switch_controller.js`が既存フォームの変更状態（画像を含む）または入力値を確認し、破棄確認の承諾後に選択POSTを送る。拒否・通信失敗はモーダル内で案内し、元のフォームを置き換えない。成功時はサーバーが返す新対象のURLへ移る。キャスト招待作成の初回店舗選択だけは既存のモーダル継続を維持する。

- 権限のない対象・存在しない対象は既存の403／404を維持し、対象情報を案内へ漏らさない。
- 選択Aで管理用B情報・B編集・B履歴などへ来ても、Bを自動選択せず、Aの内容をBのURLへ表示しない。「対象のブースをヘッダーから選択してください」と案内し、操作フォームは表示しない。選択中情報／ダッシュボードへ戻れるようにする。
- 未選択で必要操作へ来た場合は共通判定へ進む。①②なら固定先、③なら共通モーダルで選び、選んだ対象のURLへ移動する。元のURLの対象へ選択を誘導して自動確定しない。
- 古いフォームの保存先は元の対象IDに固定。選択と一致しない更新は409として理由を返し、入力を保持する。現在選択中の別対象にも、古い対象にも、黙って保存しない。画像保存・ドリンク・口座の対象にも同じ原則を適用する。
- 個別の配信セッションに属する状態変更・終了・消化は、保存済みYと対象ID・世代による既存の認可を維持する。選択IDへ配信セッションを読み替えず、終了や取消の回復経路を失わせない。
- キャストの閉鎖済み履歴の直接閲覧は既存権限の範囲で維持し、閉鎖済みを選択状態に保存しない。管理者の閉鎖済みは有効な選択として情報・履歴を利用する。
- 招待・店舗登録直後の専用導線は7節。公開プロフィールの本人編集と保存後の本人詳細への復帰は維持する。

## 7. 招待・登録・公開詳細

- #1279は本人配信中・離席中のキャスト招待承認を防ぐ。未ログインからの通常／SMSログイン復帰、ログイン済みの招待表示、承認直前を対象にする。ログイン自体は成立させ、配信を自動終了させない。
- `CastInvitationsController#show`で、ログイン復帰を含む承認画面の表示前に`AcceptInvitation.consume_if_already_member!`を呼ぶ。本人配信中・不整合なら承認ボタンを表示せず、再確認とダッシュボードへのリンクを案内する。`accept`は`AcceptInvitation.call!`のトランザクション内で改めて検証し、古い画面からの直接POSTも拒否する。
- 承認不可の場合、招待の消費・所属・ブース・担当・Stageの作成・招待先への選択変更を行わない。既に所属済みの場合に`show`が招待を使用済みにする経路も、同じ業務処理と判定へ集約する。
- 既に所属済みの表示経路も3節と同じUserロックと本人判定を通す。配信終了後、有効な招待だけを従来どおり使用済みにする。所属済みの直接承認は案内へ戻し、重複した所属・ブースを作らない。
- 準備中や初回成功確定前を本人配信と同一視せず、3節の競合を検証する。承認処理から独自のIVS照会を追加しない。
- #1274はキャスト招待の承認成功後、招待で作成した新規ブースBとその所属店舗へ選択を一緒に切り替え、B編集へ進む。有効な選択Aがあっても、この成功時だけは維持ルールとヘッダーのみの例外とする（D02）。「キャスト招待を承認しました。ブースを『〇〇店』の『B』に切り替えました。」のように、実際の店舗名・ブース名を表示する。
- 招待画面の表示、承認失敗、承認済み画面の再表示では招待先へ切り替えず、成功通知も出さない。本人配信中・離席中の承認禁止と3節の競合判定を優先する。
- 新規登録はプロフィール編集→招待で作成したBの初回編集の基本導線を維持する。業務上の初回編集対象を別タブでの選択変更によって別ブースへ代替しない。
- 店舗管理者招待と代行登録でも、業務上の対象を選択中の別店舗へ読み替えない。既存の有効選択を業務対象で上書きする処理は#1274で整理する。今回のキャスト招待制限を、店舗管理者招待の承認禁止へ無断で拡張しない。
- 公開店舗詳細の編集リンクと`return_to=store_detail`専用復帰は、新しい管理用店舗情報への編集入口を揃える#1252で廃止する。公開ブース詳細に編集リンクを追加せず、公開詳細から編集できるのは本人プロフィールのみとする。

#1279は`test/integration/cast_invitation_broadcast_guard_test.rb`で通常／SMSログイン復帰・画面表示・直接承認・準備・他者配信・既存所属・終了後の再確認を、`test/services/store_cast_invitations/broadcast_guard_concurrency_test.rb`で別DB接続の開始先行／承認先行／既存所属の消費を検証する。外部APIは模擬応答とし、実端末・実IVSの横断確認は#1277で記録する。

### 7.1 公開ブースカードと非公開店舗（2026-09-16追加）

- 有効なブースAを選択中に公開カードから別のBへ進む場合、役割・Bの管理権限によらずBの公開視聴ページへ進み、選択はAのまま維持する。ホーム・お気に入り・公開店舗詳細・プロフィールの共通カードに適用する。
- 選択中Aのカードは、担当キャストなら既存の配信準備／本人の復帰へ進み、店舗管理者・システム管理者なら従来の「視聴／配信」の選択を残す。権限のない対象は視聴のみ。未選択時は既存の共通選択・固定ルールを維持する。
- カードの閲覧と明示的な配信要求を分ける。キャストのフッター「配信」は`enter_as_cast`へPOSTし、別タブで選択が変わった古い操作を視聴へ読み替えず選択不一致で拒否する。古い管理者カードがモーダルを要求した場合も、選択外なら公開ページへの全画面移動にする。
- 非公開店舗でも管理権限に応じた選択・情報・編集・履歴は利用できる。全役割で配信準備・開始は不可とし、古い準備画面や直接URLでも拒否する。公開範囲を広げず、非公開店舗用の配信入口は追加しない。
- 準備中の店舗は非公開にでき、準備ID・作成者・タイトルを保持する。再公開まで開始不可。配信中・離席中・開始処理中のブースが店舗内にある場合、通常の店舗編集では非公開への変更を拒否する。選択中ブースだけで判定しない。
- 終了・取消・退会に伴う既存の整理は維持する。排他制御と開始境界は[実配信者設計](actual_publisher.md)を参照。

## 10. 合意した例外（2026-09-15）

### D01：店舗Bへの変更と、A店にしかない唯一のブース

前提：管理店舗A・B、ブース候補はA店の1件のみ、本人未配信。店舗Bの選択は店舗③で可能だが、ブース①を通常表示のたびに適用すると即座に店舗Aへ戻り、B店を管理できなくなる。

| 操作 | 確定する店舗 | 確定するブース |
| --- | --- | --- |
| A店からB店へ変更 | B店 | 未設定 |
| B店からA店へ変更 | A店 | A店の唯一のブース |
| B店で店舗情報・ダッシュボードを表示／再読込 | B店を維持 | 未設定を維持 |
| B店からブース情報・配信などブースが必要な操作へ進む | A店 | A店の唯一のブース。選択モーダルなし |

候補は全店舗が対象なので、最後の行はB店の候補なしで行き止まりにせず、通常の未選択時のルートでAへ自動設定する。店舗Bの管理を妨げる通常表示時のAへの補完を除去する。本人配信中・離席中は、引き続き本人のブースと店舗への固定を優先する。

### D02：選択Aがある既存キャストの招待B承認後

現行の`CastInvitationsController#accept`が行う、承認成功後の新規Bへの切替とB編集への導線を維持する。この成功時だけ、③の有効なAの維持とヘッダーのみの例外として、Bとその所属店舗へ自動切替する。

切替成功時は「キャスト招待を承認しました。ブースを『〇〇店』の『B』に切り替えました。」と店舗名・ブース名を通知する。本人配信中・離席中なら#1279で承認を止め、招待画面の表示・承認失敗・承認済み画面の再表示では選択を変更しない。新規登録はプロフィール→招待で作成したBの編集を維持する。承認成功後にAを維持してヘッダーで選び直させる案は採用しない。
