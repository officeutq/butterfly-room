# 配信終了時にIVS切断が失敗した場合の判断資料（#1281 D03）

確認日：2026-09-14。コード基準：`f1f58ec`（調査PR #1304の取り込み後）。関連：#1280、#1281、#1303。

**状態：ユーザー判断待ち。提案を実装済み・合意済みの仕様として扱わない。** #1298の外部契約調査は完了した。#1281のD03と、依存する配信制御の実装は未完了。アプリ・DB・AWS設定は本資料で変更していない。

## 1. 判断すること

IVSへの切断要求がタイムアウトや権限エラー等で成功確認できなかったとき、**アプリ上の配信終了・未消化ドリンクの返却・後続の閉鎖／退会をどこまで完了させるか**。

正常な切断成功時、通常の準備終了、実配信者Yや初回時刻の保持は既存の受入条件どおり。今回の判断は切断失敗時の利用者向け結果に限定する。AWSの権限追加の依頼ではない。

## 2. 確認した現行実装

| 入口 | 呼び出し | 現在の振る舞い |
| --- | --- | --- |
| 配信画面の通常終了・準備終了 | `Cast::StreamSessionsController#finish` → `EndService` | DB終了・現在参照解除・未消化返却・通知。サーバー側IVS切断は呼ばない |
| 店舗管理者の強制終了 | `Admin::BoothsController#force_end` → `ForceEndService` → `EndService` | IVS照会・切断の例外を捕捉し、エラーログを保存してもDB終了へ進む。画面は「配信を強制終了しました」と案内する |
| 手動のブース閉鎖 | `Admin::BoothsController#archive` | 準備中はEndService後に閉鎖。配信中・離席中は先に終了する必要がある |
| キャスト所属解除 | `RemoveCastService` → `CloseAndArchiveService` → `ForceEndService` | 対象ブースを終了・返却・閉鎖した後に所属を削除する。対象は所属キャストのブースであり、準備作成者への単純な置換はしない |
| キャスト退会 | `WithdrawalService` → `RemoveCastService` | 上記を実行し、成功後に退会を記録。外側のDBトランザクションで処理する |
| 最後の店舗管理者の退会 | `WithdrawalService#close_store!` → 所属解除・`CloseAndArchiveService` | 店舗非公開化、対象ブース終了・閉鎖、所属・招待を整理し退会を記録する |

`test/services/stream_sessions/force_end_service_test.rb` の `ends session even if IVS raises error` は、外部エラー後もセッションended・ブースoffline・現在参照なしとなることを期待している。偶然例外を見落としているという推測ではなく、現行コードと既存テストの双方で確認した。

確認コマンド：`docker compose exec -T app bin/rails test test/services/stream_sessions/force_end_service_test.rb`。結果は3件・24検証、失敗／エラー／省略0。これは現行の挙動を確認したものであり、提案した再試行方式の実装テストではない。

`EndService` の終了・返却は同じDBトランザクション内。`WithdrawalService` はさらに外側のトランザクションを持つ。IVSの切断はDBのロールバックでは元に戻らないため、途中失敗後の再試行で同じ参加者IDを扱う必要がある。成功通知も最外側のDB確定前に送らない契約へ整理する。

現行のIVS呼び出しには #1298 で確認した引数・応答形式の不一致もある。ただし、その修正だけでは「外部失敗時もDB終了へ進む」という業務上の順序は決まらない。

## 3. 比較

| 比較項目 | 案A：切断を確認してから終了・返却 | 案B：終了・返却は確定し、切断を再試行（推奨） |
| --- | --- | --- |
| IVS切断が失敗した時 | DBは未終了のまま。終了失敗と案内 | DBの終了・返却を確定し、外部切断は未完了と記録 |
| 未消化ドリンク | 切断成功後の再試行まで返却が保留される | 終了確定時に一度だけ返却する |
| 配信者・管理者への表示 | 「配信の切断を確認できません。終了を再試行してください」 | 「配信の終了と未消化ドリンクの返却は完了しました。映像の切断を再試行しています」 |
| 同じブース・同じ人物の次の配信 | 未終了の配信があるため開始不可 | 切断未確認の記録がある間だけ開始不可。理由は「前の配信の切断を確認中」と区別 |
| 閉鎖・所属解除・退会 | 切断成功まで後続処理も完了しない | DB終了・返却が成功すれば既存どおり後続へ進む。退会後も切断再試行の記録を保持 |
| 外部切断に実際は成功したが応答が消失 | 同じ参加者IDへ切断を再試行してから終了を確定 | 同じ参加者IDへ切断を再試行し、切断待ちだけを解消する |
| 現行から変わる点 | 強制終了・返却・退会がIVS障害中に保留される | 切断失敗を完了表示で隠さず、対象を限定した再試行と次回開始の確認を加える |

案Bを推奨する理由は、IVSの障害で未消化ドリンクの返却や退会まで待たせず、既存の終了・返却の意味を維持できるため。外部の切断完了は別に記録し、未確認の接続があるブースを空き扱いにしない。

いずれも切断の成功を保証する待機秒数は設けない。Stageの一律削除、全ブース停止、作成者への実績の付替えは採用しない。既に配信済みのY・初回開始時刻は保持する。

## 4. 案Bを採用する場合の具体的な処理

1. 操作対象のセッション・現在の開始要求・保存済み参加者IDと認可を確認し、終了処理が対象を確保する。古い画面の要求を現在の接続へ読み替えない。
2. そのセッションの保存済み参加者IDを切断する。未参加・重複切断も同じAPIを使う。エラー／応答不明は成功とせず記録する。
3. DBトランザクションで終了・現在参照解除・未消化返却と、必要な切断再試行の記録を確定する。IVS失敗だけでは返却を取り消さない。DB保存自体の失敗時は終了完了と案内せず、同じ対象を再試行する。
4. 最外側のDB確定後に終了・残高を通知する。切断が未確認なら未完了の案内を併記し、保存した対象へのバックグラウンド再試行を開始する。未配信と確認できる旧準備やトークン未発行の準備へ一律の外部待機を追加しない。
5. 切断待ちには元のセッション・人物・Stage・参加者IDを保持する。次の配信のIDを読み直して切断しない。終了・返却処理を切断ジョブから再実行せず、二重返却を避ける。
6. そのブースまたは人物が次の配信へ進む場合は、残った切断待ちを再確認する。成功すればその場で進み、失敗なら理由を案内して再試行可能にする。無関係な人物とブースはこの記録で停止させない。
7. 閉鎖・退会で元の利用者が操作できなくなっても、既に認可・記録された切断処理は継続する。履歴と切断対象を削除せず、管理者が対象・失敗理由・再試行状態を確認できるようにする。

単に例外を握り潰して既存処理を続ける案ではない。DB終了と外部切断の2つの結果を利用者と運用の双方が区別できることが完了条件になる。保存列、再試行の回数・間隔・失敗時の管理導線は、案の選択後にD02・D03の契約へ具体化する。

## 5. 受入条件・次の作業

- E01・E03・M01：未配信準備、Xが作った準備をYが終了する場合、旧準備の手動閉鎖を維持する。
- E02：切断成功時は同じY・初回時刻を残し、返却は一度だけ。通常終了と管理終了の認可を分ける。
- E04：既存の退会・所属解除の対象範囲を維持し、外側DBトランザクションの失敗で誤った成功通知を送らない。
- E05：IVS失敗、切断成功後のDB失敗、DB成功後の応答消失、返却後の切断再試行、退会後の切断失敗を選択した案に従って確認する。
- R03：古い終了・取消・再試行は新しい配信の参加者を切断しない。

判断後に #1281 のD03と #1303 へ選択結果を反映し、保存領域・サービス入出力・画面文言・ジョブ・全呼び出し元を確定する。D01〜D04に未決定を残して #1281 を閉じない。今回の資料は判断を具体化するための途中成果であり、アプリ実装には進まない。
