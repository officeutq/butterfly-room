## 6. 移行時の扱いと、新方式で継続して必要な回復処理

### 移行時だけの扱い

ステージング・本番のDBに配信中・離席中のセッションがないという指定を採用し、稼働中の旧配信の人物特定・接続維持・無停止引継ぎは作らない。未配信の準備と終了済み履歴を保持し、新しく開始する配信から実配信者・接続を記録する。旧準備を新方式で開始する場合もセッションIDと準備作成者は維持する。

DBの指定前提だけで、発行済み旧トークンが失効した、旧画面からの要求が来ない、IVS側の残存接続も実測済み、と読み替えない。これらは適用時の確認事項として区別する。前提に反する接続が判明した場合は対象と根拠を示して判断を戻し、通常のアプリへ一律の待機・停止を組み込まない。

記録だけの先行導入、12時間経過後の二段階切替、切替専用の開始停止・全旧画面の再読込要求は、今回の必須要件として追加しない。2026-09-14の途中調査で挙げた導入候補は、この指定前提により置き換えた。

改修後に発行する参加者ID等をDBへ保存すること、開始要求を識別すること、古い要求が現在の接続を変更しないことは新方式の通常要件として残す。移行時の稼働中配信を引き継がないことを理由に、R02・R03を省略しない。

### 採用しない近道

- 全既存ブースを12時間1分止める、旧準備を使えなくする、本人再接続に固定90秒を追加する：#1296 と合意済み受入条件に反する。
- Railsの現在参照解除・開始要求取消だけでトークンも失効した扱いにする：外部の参加権限を取り消した証拠がない。
- Stageを無条件に削除・作り直す：ブース固定方式と既存接続への影響が大きい。運用判断なしに代案として実装しない。
- 旧リクエストに接続の識別子がないまま、現在の開始要求を自動で割り当てる：古いタブの終了が新しい接続を終了する可能性を除けない（R03）。

## 7. 実接続確認の計画と範囲

隔離した検証用Stageと適用中SDKで実施した。権限不足だった初回は9節、権限追加後の結果と確認の限界は10節。既存の配信への試行や既存Stageの削除は行っていない。V03の通信断は明示的leaveなしのブラウザー終了で代替し、V06の応答消失は成功応答を利用側で捨てて再試行する条件で確認した。実回線の遮断・AWS応答パケットの破棄を実施したとは扱わない。

| ID | 確認する順序 | 記録する結果・目的 |
| --- | --- | --- |
| V01 | トークン発行 → 未参加のままDisconnectParticipant → 同じトークンで参加 | 応答、参加拒否の有無、反映時間。開始前取消で即時回復できる根拠 |
| V02 | 参加・配信 → DisconnectParticipant → 同じトークンで再参加 | SDKエラー、切断反映、別タブからの再利用可否 |
| V03 | 通常leave／通信断 → 同じトークンで再参加 → 新トークンで復帰 | 自然切断とサーバー切断の違い、二重接続、正常復帰に固定待機が不要となる条件 |
| V04 | 短い期限のトークンで参加 → 期限経過 → 接続継続と再参加を別々に確認 | 新方式でも有効期限と接続終了を区別する。時間経過だけで開始権を解放しない根拠 |
| V05 | 参加／配信／退出の各時点でGetStage・ListParticipants全ページ・GetParticipant | 反映遅延、activeSessionIdの変更、publishedの履歴性、未参加時の詳細取得可否 |
| V06 | 切断要求の応答消失／重複切断／参加との競合 | 404等の意味、同じ参加者への再試行、勝った新要求を壊さない条件 |
| V07 | 配信成功直後のDB失敗／応答消失／古い画面から遅れた操作 | 同一要求の回復、旧画面案内、準備の再利用・閉鎖・再接続を通した確認 |

V01〜V06から11節の外部契約を採用する。V07のDB連携は後続実装後に行うが、失敗の入力と期待結果は #1281 で先に固定する。通信のあらゆる競合順序、照会の反映時間上限、実回線断でのSDK内部再接続まで網羅したとは扱わない。これらの上限値を成功条件にせず、確認できない場合は対象の状態を保持して再試行する。

## 11. D01・D02へ渡す採用方法

### 人物と配信成功の確認

通常の「本人が配信中」・表示・集計は、開始成功時にDBへ確定した実配信者を参照する。準備作成者や開始権の所有者を実配信者として使わない。人物不明の旧準備だけを根拠に別ブースを拒否しない（P02・P03・M01）。

開始確定では、認証済みの人物、対象の現在セッション、保存済みの開始要求と参加者ID、IVS詳細の `role/user_id/stream_session_id` を照合する。SDKのローカル `published` を受けた通知を起点に、GetStage → ListParticipants（全ページ）→ GetParticipant → GetStageの整合を確認し、その要求の `CONNECTED/published=true` を確認する。人物・初回時刻・ブースliveを1回のDBトランザクションで保存する。`join()` 完了や任意の人物IDだけでは確定しない。

参加者不在・属性不一致・複数候補・途中失敗・Stageセッション変更は確認未完了として区別する。新しい実配信者を推測で埋めず、当該要求の確認を再実行する。実配信者と初回時刻が確定済みなら同じ結果を返し、未開始に戻さない（S03・S05・S06）。この照会を通常の一覧表示ごとに実行しない。

### 発行、取消、再接続

1. 権限・閉鎖・現在セッション・本人の別配信を検証し、同じセッションと同じ人物の競合する開始権をDBで1件に絞る。開始権は配信実績と分ける（S01・S02）。負けた発行要求が勝者を取り消す処理は設けない。
2. 発行応答の参加者ID・期限・Stage・対象セッション・認証人物・要求識別子を、ブラウザーへトークンを返す前に保存する。文字列を配布してから記録する順序は採用しない。秘密のトークン文字列をログへ出さない。
3. 未確定の開始取消・参加失敗は、要求を固定して `DisconnectParticipant(stage_arn:, participant_id:)` を呼ぶ。保存したIDへの切断成功を記録してからその開始権を解放し、同じ準備を維持する。確認済みの配信成功を取消で消さず、通常終了へ分ける（S04・S05）。
4. 再接続は同じ実配信者だけが同じセッションへ戻る。保存された以前のIDを切断してから新要求・新IDを発行する。初回時刻と実配信者は維持し、固定秒数の待機を条件にしない。以前の取消・状態変更・終了は新要求を操作できない（R02・R03）。
5. 切断応答が不明なら同じIDへ再試行する。既に切断済みでも成功することを確認済み。APIエラーや404を成功へ丸めず、対象と理由を保持する。単なるGetParticipantの404、DISCONNECTED、期限経過、leaveだけでは開始権を解放しない。

| 失敗点 | 採用する回復・保持する値 | 担当／ケース |
| --- | --- | --- |
| 外部発行前 | 成功実績を作らず開始権を取消。同じ準備を保持 | #1300／S04 |
| AWS発行応答が来ない／保存前失敗 | 未保存のトークンをブラウザーへ配布しない。発行が起きた可能性と利用者へ配布していない事実を区別する。DBに保存済みIDがある場合はそちらの切断が必要 | #1300／S04・S05 |
| ID保存後にHTTP応答が消失 | 保存済みIDを失わず、同じ要求の状態を取得。トークンを受け取れなかった場合はそのIDを切断し、新要求で再発行する。元要求の盲目的な重複発行をしない | #1300／S04・S05 |
| 配信成功通知の前後でDB保存失敗 | SDK参照を保持して同じ要求のDB状態を照会。未確定なら当該IDを切断して取消、確定済みなら保存済み人物・初回時刻を維持 | #1301／S05・S06 |
| DB確定後の応答消失 | 同じ要求への確認は既存の確定結果を返す。2回目の実績を作らない | #1301／S05 |
| 再接続途中の失敗 | 以前の切断・新規発行の記録を保持し同じ対象で再試行。配信者・初回時刻を初期化しない | #1302／R02・R03 |
| 切断失敗／応答不明 | その要求を確認待ちに残し、同じIDへの再試行入口を提供。別の正常な対象に一律の移行待機を設定しない | #1300〜#1303／S06・E05 |

ここまでを #1298 の採用結果とする。列・制約・エラー応答・取消の認可・再試行画面・終了時の返却と通知の順序は #1281 のD01〜D04で具体化し、V07の受入条件と各実装Issueへ反映する。調査完了はその設計・実装の完了を意味しない。既存の準備・閉鎖・退会経路を保持し、新たな利用制限が必要になった場合だけ根拠を示してユーザーへ戻す。
