# 旧準備・旧配信・旧トークンの移行調査（#1298）

確認日：2026-09-14。関連：#1280、#1281 の D01・D02、差し戻し #1296。

**状態：調査途中・導入方法の判断待ち。** 本書は現行コードと外部APIの調査結果であり、実装済みの仕様ではない。#1298・#1281 は未完了。アプリ、DB、AWS環境は変更していない。

## 1. 判断が必要なこと

未記録の旧トークンと、要求を識別できない旧配信画面が残るため、新方式を一度に適用する方法はまだ確定できない。**「記録だけ先行導入し、通常利用を続けながら未記録トークンの期限を待ち、配信のない時間帯に新方式へ切り替える」二段階の導入を候補とする。** 切替時には古い配信画面の再読込を求める。

これは全ブースを12時間利用不可にする処理ではない。先行導入中は従来方式で利用を続け、新方式の有効化を後日にする運用案である。ただし、切替中の新規開始を止める短い作業時間、切替日時の調整、古い画面の再読込が必要になる。これらは未合意のため、採用や実装を先に進めない。

配信を継続したまま切り替える必要がある場合は、旧接続を新しい記録へ引き継ぐ設計を続ける。現時点で「二段階なら必ず無停止で移行できる」とは結論しない。

## 6. D02に渡す移行候補と判断点

### 候補A：記録を先行導入し、配信のない時間帯に切替（推奨候補・未採用）

1. 新しい制御を利用者へ有効化する前に、既存の発行応答を維持したまま、配信用トークンの人物・対象・参加者ID・期限を保存する段階を設ける。記録を保存できなかったトークンはブラウザーへ返さない。この失敗時の案内も設計対象。
2. 全発行サーバーが記録版になり、旧コードの処理中要求がなくなった時刻を境界Tとする。通常利用を続けたまま、T以前に発行した未記録トークンの有効期間が過ぎるのを待つ。現行の既定値では12時間が基準。別の発行経路・期間指定・切り戻しがないことも確認する。経過時間だけで移行完了とはしない。
3. 配信がない時間帯に新規開始を一時止め、外部に残る配信者接続と、DBの配信・離席・処理中要求がないことを確認する。残っていれば切替を延期し、移行目的で強制終了しない。準備セッションは削除・終了しない。
4. 先行期間に発行した、なお有効な記録済みトークンを対象別に処理し、新方式と競合しない条件を確認する。未参加トークンの切断可否等は7節の実測が必要。トークン文字列は調査ログへ出さない。
5. 再接続・終了まで完成した新方式へ切り替える。古い画面からの識別子のない変更要求は新しい配信を変更させず、再読込へ案内する。同じ未配信準備から再開可能にする。

必要なユーザー判断は、**二度の導入、配信のない時間帯への切替調整、切替中の短い開始停止、古い画面の再読込を運用として許容するか**。切替時の停止時間はまだ実測できておらず、秒数を保証しない。準備の再利用は維持する。

### 候補B：稼働中の旧配信もそのまま引継ぎ

旧参加者を照合して本人・参加者IDを保存し、既存接続を維持する。未記録トークンへの対策として先行記録は引き続き検討する。旧画面には開始要求や接続世代を送る実装がないため、旧開始・離席・終了を新要求とどう区別するか、旧画面をいつ更新するかが未解決。人物が複数・不明の場合も別途扱う必要がある。現時点で実装着手可能な設計とはしない。

### 採用しない近道

- 全既存ブースを12時間1分止める、旧準備を使えなくする、本人再接続に固定90秒を追加する：#1296 と合意済み受入条件に反する。
- Railsの現在参照解除・開始要求取消だけでトークンも失効した扱いにする：外部の参加権限を取り消した証拠がない。
- Stageを無条件に削除・作り直す：ブース固定方式と既存接続への影響が大きい。運用判断なしに代案として実装しない。
- 旧リクエストに接続の識別子がないまま、現在の開始要求を自動で割り当てる：古いタブの終了が新しい接続を終了する可能性を除けない（R03）。

### 新方式の回復で確定が必要なこと

| 失敗点 | 保持する情報と回復の条件案 | 担当 |
| --- | --- | --- |
| 発行前失敗 | 実配信者・初回時刻を作らず、開始要求だけを取り消す。外部発行前である証拠を残す | #1300 |
| 発行成功・DB記録失敗／応答消失 | ブラウザーへ配布したかを区別。既に保存した参加者IDは捨てず、要求を照合して再応答または外部確認。発行不明を成功と扱わない | #1300 |
| 発行済み・未参加の取消／参加後の失敗 | 対象参加者の切断が再参加も防ぐかを実測し、成立する条件で同じ準備を再利用。単なる時刻経過・画面破棄を解除条件にしない | #1300・#1301 |
| 配信成功後のDB失敗 | 同じSDKインスタンスを保持して退出・確認。人物・要求・参加者を照合して確定済みかを再取得する | #1301 |
| DB確定後の応答消失 | 同じ要求には保存済みY・初回時刻を返す。二度目の開始実績を作らない | #1301 |
| 通信断・再読込 | 保存済みY・初回時刻を保持。旧参加者への切断と新要求の所有者を確認して復帰し、正常復帰への固定待機を設けない | #1302 |
| 切断API失敗・確認不能 | 失敗した対象・理由を保持し再確認入口を残す。別の正常な対象に移行待機を設定しない | #1300〜#1303 |

切断結果が404の場合に、未参加・不存在・既に無効をどう区別するかは未確定。開始権を解放する契約を、実測前に「404なら成功」で固定しない。

## 7. 実接続確認の残件

隔離した検証用Stageと適用中SDKで行う。既存の配信への試行、既存Stageの削除、環境設定変更はこの調査では実施していない。実施環境・対象を確定してから進める。

| ID | 確認する順序 | 記録する結果・目的 |
| --- | --- | --- |
| V01 | トークン発行 → 未参加のままDisconnectParticipant → 同じトークンで参加 | 応答、参加拒否の有無、反映時間。開始前取消で即時回復できる根拠 |
| V02 | 参加・配信 → DisconnectParticipant → 同じトークンで再参加 | SDKエラー、切断反映、別タブからの再利用可否 |
| V03 | 通常leave／通信断 → 同じトークンで再参加 → 新トークンで復帰 | 自然切断とサーバー切断の違い、二重接続、正常復帰に固定待機が不要となる条件 |
| V04 | 短い期限のトークンで参加 → 期限経過 → 接続継続と再参加を別々に確認 | 有効期限と接続終了を区別。既発行分の時間経過だけで切替しない根拠 |
| V05 | 参加／配信／退出の各時点でGetStage・ListParticipants全ページ・GetParticipant | 反映遅延、activeSessionIdの変更、publishedの履歴性、未参加時の詳細取得可否 |
| V06 | 切断要求の応答消失／重複切断／参加との競合 | 404等の意味、同じ参加者への再試行、勝った新要求を壊さない条件 |
| V07 | 配信成功直後のDB失敗／応答消失／古い画面から遅れた操作 | 同一要求の回復、旧画面案内、準備の再利用・閉鎖・再接続を通した確認 |

V01〜V06は外部契約を固定する前提確認。V07のDB連携は後続実装後に行うが、失敗の入力と期待結果は #1281 で先に固定する。代替応答の成功をこれらの実測完了に置き換えない。
