# 種類別ログ設計（#1257）

## 対象と責務

初期は `error_logs` と共通 `change_logs` の2種類。更新対象別のログテーブルは作らない。
記録はService（業務処理を集約するクラス）、閲覧認可はController（リクエストを受ける層）で扱う。
初期の実装対象は下表。一般の全更新、SQL・アクセスログ、ブラウザーエラーの収集は含めない。

| 種類 | 初期対象 | 対象外 |
| --- | --- | --- |
| 更新 | Stores::UpdateServiceを通る店舗設定編集・初回公開、Booths::UpdateServiceを通るブース作成・編集（画像を含む） | 店舗の新規登録、User、権限変更、退会・論理削除、一括更新、配信状態・在室情報、オンボーディング進捗、決済・精算 |
| エラー | Railsが報告する未処理例外、Active Jobの実行失敗・再試行、runner、配信強制終了で捕捉した外部連携エラー | Railsの4xx相当例外、入力不正、認可拒否、明示報告のない処理済み例外、メールの実到達確認 |

Stores::CompleteRegistrationSetup → Stores::UpdateService、Admin::StoresController → Stores::UpdateService、Admin::BoothsController / Cast::BoothsController → Booths::UpdateServiceが対象入口。
新規ブースの作成後に配信基盤の準備に失敗しても、既に確定したブース・作成履歴は保持する。
既存の精算イベント、決済通知、売上台帳、LP分析の履歴・役割は変更しない。過去履歴は生成しない。

## 保存項目

共通項目は occurred_at（発生日時）、created_at（記録日時）、actor_user_id、source（web/job/runner/application/ivs）、request_id、store_id、stream_session_id、archived_at。
自動処理・対象未確定の場合、実行者・関連IDは空を許容する。識別子はサーバーで決め、URLやリクエスト本文から実行者を受け取らない。
request_idは英数字・ハイフン・アンダースコア100文字まで。日時はDBへ通常のRails日時として保存し、画面はAsia/Tokyoで表示する。

更新には target_type（Store/Booth）、target_id、action（created/updated）、change_dataを保存する。
change_dataはJSONB（構造化データを保存する形式）の「項目名: [変更前, 変更後]」。変更なし・updated_atだけの変更では作らない。
1回の対象Service呼び出しで1件。画像・通常項目を同時に更新した場合も1件とし、既存の後続ブロックが失敗したら更新・履歴の双方を取り消す。

| 対象 | 保存する値 | 変更の事実だけを残す項目 |
| --- | --- | --- |
| Store | name、area、business_type、published、sales_support_company | description、address、phone_number、business_hours、website_url、x_url、instagram_url、tiktok_url、youtube_url |
| Booth | name | description |
| 両方の画像 | source_blob_id / display_blob_idのみ | 画像本体、ファイル名、署名URL、切り抜きデータは記録しない |

非公開情報になり得る項目は値を `[FILTERED]` とし、nilとの区別を保持する。変更前後を比較してから秘匿化するため、両側がFILTEREDでも変更があれば記録する。
許可していない属性は保存しない。公開名等の文字列は制御文字を除き最大1000文字、差分全体は16000バイトまで。
エラーは重要度（info/warning/error）、処理済みの有無、例外クラス、固定の安全な要約、アプリ内のファイル・行番号（最大30件）とジョブ識別情報を保存する。
任意の例外message、SQL、引数、URL、ヘッダー、リクエスト本文は保存しない。秘密情報を含む可能性があるため、既存のパラメータフィルターだけには依存しない。

## 確定・取消・障害時

- 必須更新履歴は業務と同じ接続・同じDB transaction（まとめて確定・取消する処理）で作成する。履歴保存に失敗したら業務更新も取り消す。
- ErrorLogは同じDBへの専用接続プール（最大2接続、取得待ち1秒）を利用する。業務側の外側transactionや入れ子の取消、SQLエラー状態の影響を受けずに保存する。別DBや非同期キューは追加しない。
- ログ上の実行者・対象IDには外部キーを付けない。更新中の業務行のロック待ちと、対象物理削除による連鎖削除を避け、過去の識別情報を保つ。閲覧時に対象がなければIDだけを表示する。
- DB自体が利用不能なら保存は保証できない。安全化した例外クラスとrequest_idを既存の通常ログへ出し、元の例外・応答を置き換えない。記録処理への再入を防ぐ。
- Rails.errorは同じ例外・原因の二重報告を抑止する。ジョブの別試行は別の事象としてjob_idとexecutionsを残す。
- エラー収集から新たな再試行・握りつぶしは行わない。業務確定後に外部処理が失敗した場合は、更新履歴を保持してエラーログを追加する。
- 既存の外部ストレージへのアップロードは短い業務transactionの外に維持する。更新前値は保存に使うインスタンスをロック・再取得した時点から採取する。

## 閲覧・保持

system_adminのみがエラー・更新タブを閲覧する。各タブで期間、実行者、処理元、request_id、店舗等を絞り込み、種類別の例外クラス・重要度／対象・変更区分を指定する。
初期期間は直近7日、検索期間は最大366日、1ページ50件、最大1000ページ。発生日時・IDの降順で取得する。本文の全件展開や無制限取得はしない。
ログ本文は追記専用とし、モデルによる更新・削除を拒否する。画面に編集・削除は提供しない。
物理削除はしない。通常表示の目安はエラー90日、更新365日とし、明示的な運用コマンドで古いログにarchived_atを設定する。
自動スケジュールは初期導入しない。アーカイブ済みも期間を指定して管理画面から再参照する。アーカイブは物理容量を減らさないため、容量監視と将来の保管方式は別途判断する。
必要な索引は日時、実行者＋日時、店舗＋日時、request_id、アーカイブ状態＋日時、重要度＋日時、対象＋日時。

## 検証・導入範囲

保存と取消は実際のPostgreSQLで試験する。独立接続の試験はfixtureのtransactionを無効にして、業務側の取消後もエラーが残ることを確認する。
今回はローカル実装・テスト・PR・マージまで。ステージング・本番への適用と実環境検証は実施しない。#1263にはその残作業を明記し、未確認の環境を完了扱いにしない。
